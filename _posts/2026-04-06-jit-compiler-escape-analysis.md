## 1. 객체지향의 딜레마와 메모리 성능

프로젝트에 도메인 주도 설계와 불변 객체 패턴을 적용하며 상태 변경 시마다 새로운 객체를 생성해 반환하는 방식을 사용했습니다. 도메인의 안정성과 가독성은 확보했으나 고부하 환경에서의 성능 저하 요인을 식별했습니다.

*'수천 번 반복되는 루프 안에서 매번 new 키워드로 단명 객체를 생성해도 괜찮을까? 잦은 힙 메모리 할당과 GC에 의한 Stop-The-World 현상이 시스템 병목을 유발하지 않을까?'*

과거에는 객체 풀 패턴을 도입하거나 객체 캡슐화를 포기한 채 원시 타입 필드를 직접 나열하는 식의 방어적 프로그래밍으로 이를 우회하곤 했습니다. 하지만 유지보수성을 포기하고 성능만을 좇는 설계는 장기적인 기술 부채를 동반합니다. '객체 생성이 곧 성능 저하'라는 추측에 의존하기보다 JVM 런타임 내부 분석을 통해 아키텍처 설계의 명확한 근거를 확보하기로 했습니다.

<br>

## 2. JVM의 판단: 탈출 분석과 스칼라 치환

Java 객체는 기본적으로 힙 영역에 할당됩니다. 그러나 현대 JVM의 C2 JIT 컴파일러 환경에서 이 명제가 항상 성립하는 것은 아닙니다. JIT 컴파일러는 단순 코드 형태를 넘어 런타임 실행 흐름을 정밀 추적하는 탈출 분석을 수행합니다.

탈출 분석은 메서드 내부에서 생성된 객체의 스코프 이탈 여부를 판단합니다.

* **Global Escape:** 객체가 정적 필드나 메서드 반환값으로 사용되어 외부 스코프에서 접근 가능한 상태
* **Arg Escape:** 객체가 다른 메서드의 인자로 전달되지만 해당 메서드 외부로는 탈출하지 않는 상태
* **No Escape:** 객체가 생성된 메서드 내부에서만 소비되고 소멸하는 상태

컴파일러가 특정 객체를 No Escape로 판별하면 JVM은 해당 객체를 온전한 인스턴스로 생성하는 과정을 생략하고 객체의 필드들을 개별 원시 타입 단위로 분해합니다. 이를 CPU 레지스터나 메서드 로컬 프레임 슬롯으로 분산 배치하는 과정을 스칼라 치환이라 부릅니다.

> 
> *스칼라 치환이 적용되면 객체 헤더가 제거되고 필드 데이터만 CPU 레지스터에 할당됩니다.*

결과적으로 물리적 힙 할당 자체가 생략되므로 가비지 컬렉션의 수거 대상 자체가 발생하지 않습니다.

## 3. JMH 마이크로 벤치마크 실험

스칼라 치환의 메모리 영향을 정량적으로 검증하기 위해 JMH로 실험 환경을 구축했습니다.

```java
@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.NANOSECONDS)
@State(Scope.Thread)
public class EscapeAnalysisBenchmark {

    static class Point {
        int x, y;
        Point(int x, int y) { this.x = x; this.y = y; }
    }

    private int a = 10;
    private int b = 20;

    @Benchmark
    public void testScalarReplacement(Blackhole blackhole) {
        Point p = new Point(a, b);
        int result = p.x + p.y;
        blackhole.consume(result); 
    }
}

```

JMH의 `-prof gc` 옵션을 통해 탈출 분석 활성화 여부에 따른 메모리 할당 지표를 계측했습니다.

| **실험 케이스** | **JVM Options** | **평균 응답 시간** | **작업당 힙 할당량 (B/op)** | **GC 발생 횟수 (1분당)** |
| --- | --- | --- | --- | --- |
| **Case A (최적화 OFF)** | `-XX:-DoEscapeAnalysis` | `3.007 ns/op` | `24.000 B/op` | `704 counts` |
| **Case B (최적화 ON)** | `-XX:+DoEscapeAnalysis` | `0.938 ns/op` | `≈ 10⁻⁶ B/op` | `≈ 0 counts` |

Case A에서는 Point 객체 생성 시마다 메타데이터와 필드를 포함해 약 24바이트의 단명 객체가 Eden 영역에 반복 적재되었습니다. 반면 탈출 분석이 활성화된 Case B에서는 힙 할당률이 0바이트로 수렴했습니다. 힙 메모리 할당 및 역참조 비용이 소거되어 응답 속도가 약 3.2배 단축되었습니다.

## 4. 기계어 수준의 확인: 어셈블리 코드 분석

`hsdis` 플러그인을 활용해 C2 JIT 컴파일러가 생성한 x86 어셈블리 기계어 코드를 역추적했습니다.

<br>

**최적화 이전: 힙 할당 방식 (Escape Analysis OFF)**

객체 생성을 위해 TLAB 여유 공간을 확인하고 힙 메모리에 객체 헤더를 기록합니다.

```assembly
; TLAB 여유 공간 확인
0x00007f...: mov    r10, QWORD PTR [r15+0x60]   
0x00007f...: lea    r11, [r10+0x18]             ; 24바이트(헤더 16B + 필드 8B) 할당 주소 계산
0x00007f...: cmp    r11, QWORD PTR [r15+0x70]   ; TLAB 한계 초과 시 느린 할당 루틴 호출

; 객체 헤더(Mark/Klass) 및 필드 데이터 기록
0x00007f...: mov    QWORD PTR [r10], 0x1        ; Mark Word 초기화
0x00007f...: mov    DWORD PTR [r10+0x8], 0x...  ; Klass Pointer 등록
0x00007f...: mov    DWORD PTR [r10+0xc], r8d    ; 필드 x 값 기록
0x00007f...: mov    DWORD PTR [r10+0x10], r9d   ; 필드 y 값 기록

```

`new Point()` 호출 시 TLAB 메모리 경계 계산, 객체 헤더 설정, 메모리 쓰기 등 상당한 하드웨어 사이클이 소모됩니다.

<br>

**최적화 이후: 스칼라 치환 적용 (Escape Analysis ON)**

탈출 분석과 스칼라 치환이 적용된 컴파일 코드는 다음과 같습니다.

```assembly
; 힙 할당 및 객체 헤더 기록 명령어 소거
0x00007f...: mov    eax, DWORD PTR [r12+0x10]   ; 변수 a를 eax 레지스터로 로드
0x00007f...: add    eax, DWORD PTR [r12+0x14]   ; 변수 b를 더함 (x + y)

```

힙 메모리 할당(`lea`, `cmp`)과 메모리 쓰기 명령어 전체가 사라졌습니다. 컴파일러는 Point 객체를 힙에 할당할 필요가 없다고 판단하여 필드 값만 CPU 레지스터(`eax`)로 직접 로드해 덧셈 연산을 즉시 종결했습니다.

<br>

## 5. 스칼라 치환이 적용되지 않는 예외 조건

JIT 컴파일러의 스칼라 치환 최적화가 모든 런타임 상황에서 보장되는 것은 아닙니다.

1. **객체 크기 한계 초과:** 치환할 필드가 너무 많아 CPU 레지스터나 스택 프레임에 적재할 수 없는 경우 (JVM 내부 한계 임계치 초과 시)
2. **복잡한 제어 흐름:** 객체 생성과 소비 사이에 복잡한 분기나 반복문이 중첩되어 제어 흐름 분석 단계에서 객체의 생명주기 및 비탈출 상태를 명확히 판별할 수 없는 경우

메서드의 호출 깊이가 지나치게 깊거나 인라인화가 실패하면 탈출 분석의 스코프 역시 무너지게 됩니다.

<br>

## 6. 결론: 런타임 환경 중심의 엔지니어링

애플리케이션 계층에서 메모리 성능을 개선하겠다고 인위적으로 객체 풀링을 적용하거나 절차지향적으로 코드를 비틀어 작성하는 것은 오히려 JIT 컴파일러의 인라이닝과 탈출 분석을 방해할 수 있습니다.

성능 확보를 위해 맹목적으로 객체 생성을 기피하기보다 메서드를 작고 응집도 높게 유지하여 JIT 컴파일러가 기계어 수준으로 최적화하기 좋은 코드를 작성하는 것이 객체지향 설계와 고성능을 동시에 달성하는 올바른 길입니다. 프레임워크의 편의 기능에 안주하지 않고 작성한 코드가 하드웨어와 런타임 계층에서 실제로 어떻게 실행되는지 추적하고 통제하는 시야가 중요합니다.
